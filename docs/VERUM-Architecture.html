VERUM OS Architecture

How a capability-secured, content-addressed, ledger-driven operating system works, file by file, with the flow of control drawn out.

Two implementations of one design: verum/ (hosted, Python 3.10+) and metal/ (bare-metal x86, C, boots in QEMU). Project root: D:\OS system.

1. What VERUM is

VERUM is an operating system built from four decisions that Windows, macOS/iOS, Android and Linux all made the other way. Each decision removes a whole class of attacks by construction rather than by patching, and each one also makes work on the system reproducible, traceable and undoable.

The design is small enough to hold in your head: a store of immutable objects named by their content, a ledger that records every change, a capability table that is the only source of authority, a virtual machine that is the only thing programs may run in, and a kernel that moves messages between programs (called cells) and checks every request against the capability table. A shell is the human's seat: it holds capabilities like any other principal and issues intents.

There is no root user, no file path, no process, and no native code anywhere in the system. If you are looking for those, this document explains what replaced them and why.

2. The four rules

RULE 1

No files, no paths

Every object is immutable and named by the SHA-256 of its content. You find things by tag or by provenance, never by location. Changing a byte changes the name, so nothing can be silently tampered with and nothing can be overwritten.

RULE 2

No root, no users: capabilities

A principal can do exactly what the unforgeable tokens it holds allow. Tokens are narrowed when passed on, never widened, and revoking one revokes everything derived from it. There is no privilege to escalate into.

RULE 3

No apps, no processes: cells

A cell runs only Verum Script inside a kernel-owned interpreter with a CPU budget (fuel), a memory budget and a depth budget. It has no memory between messages and exactly one door to the world: (call <cap> "op" …).

RULE 4

The ledger is the system

Every change is an event in a hash-chained log. Booting is replaying the log. verify proves nobody edited history; rewind N forks the whole system at entry N.

3. System architecture

The system is five layers. Each layer talks only to the one below it, and every arrow that crosses from a cell toward the kernel passes through one function: the syscall gate.

Principals

Anything that can hold a capability is a principal. There are two kinds: seats (humans; the one named shell is seated at genesis with a store, console, clock and kernel capability, and further seats start with nothing) and cells (programs, also born with nothing). The kernel is not a principal; it is the referee. On bare metal the shell shows the active seat in its prompt and switch changes it; every intent is then checked against that seat's capabilities.

5. Flow: boot

Both implementations boot the same way in spirit: establish the runtime, seat the shell with its genesis capabilities, then either replay the ledger (hosted) or load the embedded code objects (bare metal), and drop into the shell.

Genesis

Genesis is the one event that creates authority from nothing. The kernel mints four capabilities for the principal named shell, one per kind, each with the full right set of its kind: store[get,put,find,lineage], console[print], clock[now], kernel[spawn,mint,revoke,cells]. No cell capability exists yet, because no cells exist. From this point on, every capability in the system is either one of these four or a descendant of one of them, which is why revocation can always find its way back to the root.

6. Flow: a message through the system

Work in VERUM is message passing. The shell (or a cell holding a cell capability) queues a value into a cell's inbox; the scheduler later runs the cell's on-message handler on it. The figure follows the demo pipeline: a note goes to shout, which stores an upper-cased copy and forwards its hash to wc, which stores a stats object.

The scheduler

Hosted: run loops while any cell has a pending message and the tick limit is not reached. Each tick, every cell with a non-empty inbox gets exactly one message, run to completion inside its fuel budget (50,000 steps; a syscall costs 10).

Bare metal: the scheduler is preemptive. Every cell with work gets its own kernel stack, and each run round hands every runnable cell a 50 ms slice. When the timer expires the slice it sets vm_preempt; the VM's burn() sees the flag at its next step and calls task_yield(), which ctx_switches back to the scheduler with the cell's whole interpreter state left in place on its stack. The next slice resumes it exactly there. Because yielding only happens between VM steps, a syscall is never interleaved with another cell's: the ledger records effects in the order they truly happened, and replay (which never re-executes code) stays deterministic. Fuel is 2,000,000 steps per message; memory is bounded by the cell's arena (below).

In both, when a handler raises, runs out of fuel, exceeds the size, memory or depth budget, the kernel prints cell X stopped: reason, counts an error for the cell, and records a ran event with ok=false. The kernel itself never stops. Cells are stateless between messages on purpose: the only memory is the store, so any run can be reproduced from its inputs.

Arenas: memory per message

With preemption a cell can use its whole fuel budget, and the kernel's bump allocator never frees. So each cell owns an arena (8 MiB): while that cell runs, every allocation lands there, and the arena is reset when its next message starts. Values that must outlive the run are deep-copied into the persistent heap at the moment they cross the boundary: an object's data on store_put, a message body on send, the text of a ledger line, a capability binding. Filling the arena ends the run with memory budget exceeded through the usual error path. This is the real memory bound for a cell; the size budget on strings and lists remains as a cheap early check.

7. Flow: the syscall gate

A cell can affect the world in one way: (call <cap> "op" args…). The VM evaluates the arguments, charges ten fuel, and passes the capability handle, operation name and arguments to the kernel's syscall function bound for that cell. Everything hinges on what happens next.

Two details make the gate airtight. First, a cell receives capabilities only as CapHandle values bound into its environment by the kernel at grant time; the VM has no builtin that creates one, and str on a handle prints <cap label>, never the token. Second, store.put performed through the gate stamps the object with by = calling cell and op = "run"; a cell cannot forge provenance any more than it can forge a capability.

8. Flow: capability lifecycle

Delegation between cells

A cell may pass a narrower copy of a capability it holds to a cell it is linked to, if the capability carries the delegate right:

(call store "delegate" next "get" "store")   ; next: a cell→x[send] capability; "store": the label bound in x

The gate checks four things: the caller holds the capability with delegate; the second argument is a cell capability the caller holds; the requested rights parse for that kind; and attenuate accepts them as a subset of the caller's. The new capability's parent is the delegating cell's own copy, so the revocation tree is unchanged: revoke the original and the delegated copy dies with it. The same syscall exists in the hosted kernel with three tests. Delegation does not require the shell, which makes cell pipelines self-assembling without widening anything.

How the claims are tested

The security story rests on three invariants, and tests/fuzz.py attacks all three with random input. Each iteration builds a random world (1–4 cells from random or deliberately broken Verum Script, random grants with random right subsets, random links, random notes), sends random messages, runs the scheduler, then checks:

  1. Containment: nothing but VMError, CapError or KernelError escapes; the kernel never raises anything else.
  2. Authority: every handle a cell holds names a capability whose holder is that cell, whose rights are a subset of its parent's all the way up to a genesis capability, and no wider than what the shell actually granted; a revoked capability is refused on the next use.
  3. Integrity: the ledger verifies, and a kernel rebuilt by replaying it has the same objects, cells, capabilities and revocations.

Its first sweep found a real containment bug: a cell could put or send a value containing a capability handle or a closure, and the ledger's encoder raised a TypeError that escaped the run. Authority was never leaked (a smuggled handle fails the holder check), but a crash is exactly what invariant 1 forbids. Both kernels now flatten any value that crosses into the store or an inbox. CI runs 3,000 iterations on every push; --forever runs until stopped.

9. Data model: objects and the ledger

An object

{
  "kind":   "stats",
  "data":   {"words": 9, "chars": 43},
  "tags":   ["stats"],
  "by":     "wc",            stamped by the gate
  "op":     "run",
  "inputs": ["7889982f5dfd…"],   provenance
  "tick":   2
}
hash = sha256(canonical(json))  →  the object's only name

Canonical form (sorted keys, no whitespace, same escaping) is what makes the name stable: two principals writing the same stats from the same input get the same hash, and the store keeps one copy. why <hash> walks inputs recursively and prints the tree.

A ledger entry

{
  "seq":   27,
  "prev":  "e639510d81…",        hash of entry 26
  "event": {"type": "ran", "cell": "mal",
            "tick": 4, "fuel": 40, "ok": false,
            "error": "denied: capability lacks right 'get'"},
  "hash":  "daa5e4d9bd…"         sha256(seq, prev, event)
}

Event types: genesis put mint grant revoke spawn kill send ran tick. verify recomputes every hash and checks each prev. Editing any entry breaks every hash after it.

On bare metal: the ledger on disk, and rewind

The bare-metal kernel keeps the same event log on a raw disk attached as the primary ATA master. There is no filesystem in between: the disk is the ledger. Each event is one text line; object data inside a line is serialized as Verum Script ((dict "words" 9 …)) so the kernel's own reader parses it back on replay.

The attic: rewind without loss

Before the ledger is shortened, kernel_rewind appends the entries it is cutting off to the attic stream (sectors 8192–16383), introduced by a branch|from|count|uptime line. attic lists the branches; restore k re-applies branch k through the normal replay path with write-back enabled, so the entries return to the ledger and the disk in their original order. A restore is accepted only when the ledger length equals the branch's from: anything else would splice events onto a history they were not recorded against. Branches stay in the attic after a restore, so the attic is append-only like everything else. This replaces the destructive rewind of the first bare-metal version and matches the hosted kernel's fork semantics in effect, on one disk.

The small UI

Row 0 is a status bar, refreshed after every command: object count, cell count, ledger length, tick, and how many entries the disk holds (or none (RAM only) when no disk is attached). history prints the whole timeline with entry numbers for rewind. dash replaces the console with a panel: cells on the left (green when error-free, yellow otherwise, with the labels of the capabilities they hold, ! marking a revoked one), the newest 18 ledger entries on the right, and store and disk totals below; any key returns to the shell.

10. The Verum Script VM

Cells cannot run native code or Python, because a cell with access to either could reach around the capability table. Verum Script is a small Lisp whose interpreter is owned by the kernel and whose values are only numbers, strings, lists, dictionaries, closures and opaque capability handles.

Why there is nothing to escape to

  • Builtins operate on plain values; none of them touches Python objects, modules, I/O or memory. The C version has no libc to reach.
  • No mutation primitives: no set!, no mutable cells. State lives in the store or nowhere.
  • Symbols that are not bound raise unbound symbol; (__import__ "os") is just an unbound symbol.
  • Errors are exceptions in Python and longjmp in C; in both, the interpreter frame is discarded and the kernel's own frame continues.

Hosted kernel (Python)

Requires Python 3.10 or newer and nothing else.

Bare-metal kernel (C, x86)

Requires NASM, LLVM (clang + ld.lld) and QEMU. On Windows:

winget install NASM.NASM
winget install LLVM.LLVM
winget install SoftwareFreedomConservancy.QEMU
cd metal
python build.py          # build only → build/verum.elf (~57 KiB)
python build.py run      # build and boot in a QEMU window
python build.py test     # boot headless, work, kill QEMU, reboot from disk, rewind, reboot, dash; dumps build/*.png

The build creates build/verum.img, an 8 MiB raw disk, and attaches it as the primary ATA drive. Delete it to start from a blank system; build.py test always starts from a blank one.

build.py looks for the tools on PATH and in their default install folders. The kernel is loaded by QEMU's -kernel option, which understands Multiboot ELF files directly; no ISO or bootloader image is needed.

13. Shell reference

Commands are intents, not programs. Hashes may be typed as any unique prefix of at least four characters. py marks commands only in the hosted shell; metal marks bare-metal-only ones.

note <text>
Store a note object tagged note.
code <name> <path.vs> py
Syntax-check a Verum Script file and store it as a code object tagged code and <name>.
code metal
List the code objects embedded in the kernel image.
find <tag>
List objects carrying a tag.
tags
List every tag with its object count.
show <hash>
Print kind, tags, creator, operation, tick, inputs and data of an object.
why <hash>
Print the provenance tree: the object, what it was made from, recursively.
spawn <cell> <code>
Create a cell from a code object (by hash or by name). It starts with no capabilities.
grant <cell|seat> <cap> [rights]
Attenuate one of your capabilities to the listed rights (default: all you hold) and bind it in the cell, or in the seat, under the capability's name. Add delegate to let a cell pass it on. Example: grant wc store get,put.
link <a> <b> [label]
Mint a cell→b[send] capability and give it to a, bound as label (default b). shout.vs expects the label next.
send <cell> <expr>
Evaluate a pure Verum Script expression (no capabilities) and queue the value for the cell. Bare metal also accepts @tag: the hash of the newest object with that tag.
run [rounds]
Drive the scheduler until no cell has work or the round limit (default 100) is reached. On bare metal a round is one time slice per runnable cell; cells paused mid-run resume on the next run.
cells
List cells with run/error/fuel counters and every capability each holds.
caps
List your own capabilities.
revoke <cell> <label>
Revoke the capability bound under that label in that cell, and everything derived from it.
kill <cell>
Remove a cell.
eval <expr>
Run Verum Script in the shell with your own capabilities bound as store, console, clock, kernel. The hosted shell lists which capabilities were used.
ledger [n]
Show the last n ledger entries.
verify
Recompute and check the whole hash chain.
rewind <n>
Hosted: fork the system at ledger entry n into a new state directory and switch to it; the original is untouched. Bare metal: show the entries that will move to the attic, ask you to type yes, then rebuild from the first n entries and shorten the disk ledger. Needs kernel[revoke].
attic metal
List the branches cut off by earlier rewinds, marking any that can be restored from the current point.
restore <k> metal
Re-apply branch k; only when the ledger is at that branch's starting point.
seat <name> [passphrase]
Create another human principal with no capabilities, optionally locked with a passphrase (only a salted hash is stored). Needs kernel[mint].
switch <name> [passphrase]
Put that seat at the keyboard; the prompt changes and every intent is checked against its capabilities. Every attempt is a login ledger event, failed ones included.
seats · whoami
List seats and their capabilities; print the active seat.
alarm <cell> <seconds> <expr> metal
The clock sends cell the value of expr every seconds (sender name clock). Recorded in the ledger. alarms lists, unalarm k removes. Needs kernel[mint].
bg on|off metal
Run cells and fire alarms while the shell waits for a key. Output produced in the background goes to log (and log clear) rather than over your prompt; the status bar counts waiting lines.
history metal
The whole ledger as a numbered timeline, for choosing a rewind point.
dash metal
Full-screen panel: cells and their capabilities, ledger tail, store and disk totals. Any key returns.
uptime metal
Milliseconds and timer ticks since boot, and the per-message time slice.
trap metal
Deliberately raise a divide-by-zero in the kernel to show the exception panel. The machine halts; the disk is intact.
mem metal
Heap used, object, capability and ledger counts, entries on disk.
demo metal
Run the scripted tour (hosted: python -m verum demo).
help · quit

14b. संस्कृतलिपि: programming in Sanskrit

Verum Script is a Lisp. Its syntax is nothing but parentheses, and everything inside them is a word, so the language can be given a second vocabulary without touching the evaluator. verum/sanskrit.py names every special form, builtin, standard capability label and operation in Sanskrit; the reader (vm.parse in Python, read_form in C) maps each Sanskrit symbol to its canonical form as it is read, and Devanagari digits (०–९) become numbers. Operation strings inside (call …) are mapped at the syscall gate.

The consequence is exact: a program written in Sanskrit and the same program written in English parse to the same forms, so they have the same behaviour, the same hash in the store, the same provenance and the same capability needs. cells/ganana.sv is the word counter in Sanskrit; the test suite runs it beside wordcount.vs and checks that both produce the same stats.

In the hosted shell, sanskrit <file.vs> renders an English program in Sanskrit, and code name cells/ganana.sv loads a Sanskrit one. On bare metal the Sanskrit cell is embedded in cells.c and runs the same way.

Showing Devanagari on bare metal

VGA text mode has 256 fixed glyphs and cannot draw Devanagari, so the kernel has a framebuffer console (fb.c). Proper Devanagari needs shaping: क + ् + ष becomes the conjunct क्ष, and the vowel sign ि is drawn before the consonant it follows in the text. A kernel this size should not carry a shaping engine, so shaping happens at build time: fontgen.py asks Windows GDI (Nirmala UI) to render every Sanskrit word the kernel can show — the whole vocabulary plus every Devanagari word in the embedded cells — and stores each as a 1-bit bitmap in font.h, alongside an 8×16 ASCII font. At run time the console draws ASCII glyph by glyph and Devanagari word by word from that atlas; a word it has never seen shows as one box per code point. The trade-off is explicit: perfect rendering for a known vocabulary (~90 words, 68 KiB), not arbitrary text. Sanskrit cell output and show of Sanskrit source both display correctly in QEMU.

15. Writing a cell

A cell is a code object whose top level defines on-message. The handler receives the sender's name and the message body. Capabilities are plain names in the environment, bound by grant and link; the names the code uses must match the labels the shell binds.

; cells/wordcount.vs — needs: store[get,put]  console[print]
(define (count-words text)
  (len (split text " ")))

(define (on-message from body)
  (let ((obj   (call store "get" body))
        (text  (get obj "data"))
        (stats (dict "words" (count-words text)
                     "chars" (len text))))
    (call console "print" "counted" (get stats "words") "words in" (slice body 0 12))
    (call store "put" "stats" stats (list "stats") (list (get obj "hash")))))

Notes for authors:

  • Pass the hashes you read from as the fourth argument of put; that is what makes why work and what makes results reproducible.
  • Keep per-message work under the fuel budget (50,000 steps). Large inputs should be split across messages rather than processed in one run.
  • A cell has no state between messages. If you need to accumulate, put an object, tag it, and find it next time.
  • To chain cells, ask the shell for link a b label and call (call label "send" value). A cell can only reach cells it has been linked to.
  • Hosted: save as cells/name.vs, then code name cells/name.vs and spawn x name. Bare metal: add the source to cells.c and rebuild; there is no filesystem to load from.

17. Limits and next steps

The security claims are about the model: a cell cannot escape Verum Script, and nothing happens without a capability. They hold as far as the interpreter and the gate have no bugs. Neither implementation has been audited.
  • Bare metal has no paging or network. It is single-core; the disk driver is PIO on the primary ATA bus, one sector per transfer. Cells are isolated by the VM and by their arenas, not by hardware: paging would add a second wall that holds even against an interpreter bug. The next natural steps, in order: paging with per-cell address spaces; alarms in the hosted kernel for parity; then a capability-gated network device.
  • Interrupt handlers do the minimum. The timer only counts and sets a flag; the keyboard only queues a scancode. All real work happens in the kernel's normal flow, which keeps the ledger and the VM free of reentrancy concerns.
  • The hosted version is a model of a machine, not a machine. Its purpose is to prove the design and to be the reference for the port.
  • Scheduling is round-robin without priorities. On bare metal a cell is paused after 50 ms and resumed later, so no cell can starve the rest; fuel and the arena bound each message. Live interleaving is nondeterministic (as on any OS), but the ledger records the order that actually happened, so replay is exact.
  • The genesis seat is trusted. shell holds the genesis capabilities; other seats hold only what it grants them. A seat may carry a passphrase (salted SHA-256; never stored in clear), and every login attempt is recorded. The shell seat itself has no passphrase yet; giving it one is a one-line change in genesis.
  • Booting a physical PC from USB needs a GRUB image around the same verum.elf; the kernel itself does not change.
